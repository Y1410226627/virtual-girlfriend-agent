# ADR 0003：数据库迁移只追加、只加列、启动自动执行

## 背景
单用户本地 SQLite 库（`data/girlfriend.db`）承载着不可再生的用户数据（聊天、记忆、关系状态）。
没有 DBA、没有备份服务；用户不会执行任何手工 SQL。

## 决策
- 迁移定义在 `src/lib/db.ts` 的 `MIGRATIONS` 数组，**只允许在末尾追加**新版本（v1…v11…）。
- 迁移必须**幂等**（`CREATE TABLE IF NOT EXISTS` / 先检查再 `ALTER`），应用启动时自动按序执行，
  已执行版本记录在 `schema_migrations`。
- **只允许加表、加列**；删除/重命名列等破坏性变更必须拆两步（先停止使用 → 下一个版本再删）。
- 不修改历史迁移条目（老库重放会不一致）。

## 理由
- 用户数据不可重建：任何「删库重来」式方案都不可接受。
- 零运维：升级路径必须是一条命令（双击 启动.cmd）内自动完成，且失败不破坏已有数据。
- 历史经验：项目 v5→v6→v8 对边界表「删了又建」的教训说明破坏性迁移最容易出事，故一律禁止。

## 影响
- 表结构会长期保留一些「历史遗留列」，属可接受代价。
- 新增结构（如 v11 的 life_arcs / agent_diaries / cast_json）都按此流程追加，实测冷启动自动升级正常。

## 替代方案
- 外部迁移工具（Prisma / Drizzle 等）：新增依赖 + 原生模块风险，与「零原生依赖」冲突。
- 手工 SQL 脚本：用户不可执行，排除。
