# ADR 0005：回合/生成/操作账本（Turn Engine）+ 持久化分析任务 + 本地安全边界

## 背景
2026-10-06 的第三方深度审查（《虚拟女友优化建议》）逐文件追调用链后指出：功能密度已经很高，但「这一轮对话到底发生了什么」没有统一的事实源，导致一组表面上互不相关的缺陷：
1. 并发/重复请求下，`prepareTurn` 可同时读到不同历史；生成失败会留下"幽灵 turn"（状态已改、消息已删）。
2. 「重新生成」被实现为"新的一轮"：多消耗 turn_count，旧生成的记忆/关系影响不撤销，可能产生两套历史影响。
3. 分析任务只是内存队列：服务器重启即丢失；超过上限静默丢弃。
4. 删除/撤回依赖"快照差 + 数值相等"推断回滚，会误伤其它轮次的变化（如人格 50→51→52→51 的场景）。
5. `/api/analyze` 相信客户端传来的对话文本；任意客户端可凭空写入系统状态。
6. 任意 Base URL + 已保存 Key 的组合存在把凭据发往未知主机（outbound）的风险；GET 路由会触发写库。

## 决策
### 1. 新增四张表（只加表，见 v12 迁移）
- `conversation_turns`：一轮对话（一个用户消息 = 一个 turn；sequence 递增）。
- `message_generations`：同轮的各次生成（重新生成 = 新 generation，旧的标 `superseded`；`turn.current_generation_id` 指向当前）。
- `analysis_jobs`：分析任务持久化（pending/running/done/failed/cancelled + attempts/next_retry_at）。
- `turn_operations`：操作账本（每个真实状态变化的 before/after 与来源 turn/generation）。
不修改任何历史迁移；旧数据不迁移，读取处对缺行/缺列做兼容。

### 2. 服务端会话锁（`withConversationLock`）
同一用户的整条生成链路（prepare → 生成 → 落库 → 提交 → 入队 → 出错清理）在服务端串行执行（进程内 Promise 链，挂 globalThis 防 HMR 丢失）。客户端锁只防单标签页，不能防多标签页/脚本/重复 POST。

### 3. prepare 去副作用 + 只在成功后提交
`prepareTurn` 只读 + 计算；`commitTurn`（assistant 成功落库后）才写 turn_count / touchInteraction / 场景（含 TTL）。时间驱动的世界推进（生活/事件到期）留在 prepare——它是按流逝时间幂等推进，不是"本轮的产物"。

### 4. 分析任务持久化 + 版本校验
`analysis_jobs` 是队列事实源；执行前校验「assistant 消息仍存在 && generation 仍是 current && turn 未取消」，否则标 `cancelled` 且不落任何影响。失败退避重试（1/5/15 分钟，最多 3 次）；服务器重启把遗留 running 改回 pending 继续跑；取消"队列满静默丢弃"。分析文本一律由服务端按 messageId 从库里读（不再信任请求体）。

### 5. 操作账本与精确回滚
分析应用阶段在一个事务内完成（网络调用全部前置），并逐实体记录 `turn_operations`。删除/撤回优先按账本反向（记忆按 id、人格/依恋按 old/new、银行按实际 delta、冲突按 status、共享世界恢复 before 快照）；**没有账本的历史数据保留原有推断式回滚作为兜底**。多源累积形成的人格/依恋调整（`source_turns` 跨越多个回合）不随单条消息回滚。

### 6. 本地安全边界
- dev/start 默认只监听 `127.0.0.1`；可选 `ACCESS_PIN`（设置后启用 middleware 门禁，未设置时完全放行）。
- 「已保存的 Key」绑定保存时的 host（`llm_key_host` / `embedding_key_host`）；目标 URL 换 host 后不再自动携带旧 Key（回退环境变量），避免改地址即泄露凭据。
- GET 路由只读；后台推进改由 `POST /api/tick` 触发（前端加载时调用一次 + scheduler 周期推进）。

### 7. 自定义模式（模式 B）冻结范围
`custom_mode` 开启时冻结全部自动数值漂移（关系/性格/依恋/亲密 + 生活/健康/心理），但保留记忆、日记与叙事（它们不是"数值"）。

## 理由
- 并发/重试/失败会"逐渐变脏"是长期陪伴类应用的根风险；先有事实源（turn/generation/operation），后续的记忆、人格、生活、主动消息才能作为 projection 挂上来，而不必推倒重写。
- 持久化任务 + 版本校验把"丢失/错位/重复应用"从概率问题变成可判定问题。
- 精确回滚是「删除消息」这个高频操作的信任基础：删除必须可解释、可复现。
- 本地优先应用不做公网级认证，但默认不对外监听 + 可选 PIN + 凭据与地址分离，成本低、风险面显著收窄。

## 影响
- 数据库新增 4 张表 + 若干列（追加式迁移，向后兼容旧库）。
- `/api/chat` 的 `done` 事件新增 `turnId/generationId/analysisJobId/analysisStartedAt`；前端据此轮询分析进度，不再主动 `POST /api/analyze`（接口保留兼容，只接受 messageId）。
- 新增回复校验层（低分自动重答一次，最多一次）；主动消息会触发一次轻量"自我暴露"抽取（她自己的话进入她自己的记忆/计划）。
- 删除/撤回语义更精确：删除用户消息 = 撤销该轮全部 generation 的影响；删除她的回复 = 只撤销该次生成。

## 替代方案
- **引入正式 ORM / 事件溯源框架**：与"零原生依赖、单文件可跑"的定位冲突，且大爆炸重构违背小步可回滚原则。
- **用文件锁/外部数据库做跨进程锁**：本地单机场景收益极低；改为"禁止 PM2/cluster 多实例 + DB 租约"即够。
- **只靠父子进程内存队列 + 定时重扫**：重启即丢任务的问题无法根治，故选择落库。
- **共享世界拆成规范表**：暂缓（事务化读改写已消除丢更新），列入技术债，待有真实需求再做双写过渡。
